# Design decisions

The choices behind FlyBot on AWS and why they were made. Superseded choices are kept in short, with what replaced them.

## Vision Lambda and agent

| Decision | Why |
|---|---|
| The vision Lambda is **stateless**: one invocation = one photo. The camera's recent counts come in the request (`history`), proposals go back in the response; no queue, no database of its own | FlyBot (MongoDB) already owns cameras, photos, approvals and traces; the Lambda needs only one photo and its recent context, so it scales to zero and has nothing to migrate |
| The agent's device and FlyBot tools answer "pending": every accepted action becomes a **proposal** in the response (`capture_now`, `set_isp`, `set_interval`, `review_request`, `notify`); the rule and LLM planners and the guardrails run as before each call | Keeps the perception -> decision -> guarded action -> trace loop while FlyBot stays the only system that acts on cameras and asks people (confirm cards) |
| `requiresApproval`: `capture_now`, `notify`, `review_request` false; `set_isp`, `set_interval` true. `confidence` per decision rule (`lambda/vision/sentinel/agent/policy.yaml`) | One extra photo within the guardrails' daily budget is low risk; image settings and schedules affect battery and image quality. These are policy values, not measurements |
| Op 2 glare on a **lure tray floor** has its own limit, `glare.floor_ratio_max` 0.05 of the floor (sticky cards and whole frames keep `glare.ratio_max` 0.02); the score `glare_region` says which one applies, and scores without it get the strict limit | The agronomy advisor rejected a recapture of a countable photo with 3.4 % floor glare (`eval/RESULTS.md` section 6). At even fly density, 5 % hides at most 1 fly in 20, under one fly at every lure count in the export (max 10); the failure-injection reflection (8.3 % of the floor) still flags. A policy choice, not a calibration: no human glare labels exist. Before vs after on the same photos: `eval/results/glare_rule_ab.json` |
| `set_isp` only for `camera.platform == "camos"` | EZVIZ cameras expose no image settings through FlyBot; a plain KVS stream has no control channel |
| Errors are raised as `VisionError` subclasses whose message is the contract JSON (Lambda `FunctionError`, `errorMessage`); the local server maps them to HTTP 400/404/503/500 | `Lambda.Invoke` has no status code; FlyBot reads one field in both transports (`docs/CONTRACTS.md` 1a) |
| Photos are decoded before the agent runs, once | `photo_not_found` and `bad_request` are reported as such instead of surfacing as a tool error inside the agent |
| Evidence pictures go to the bucket the photo came from (else the Lambda's `PHOTOS_BUCKET`) | FlyBot serves evidence from its own bucket |
| LLM: Anthropic `claude-haiku-5-5` with prompt caching, key from Secrets Manager. Deep mode (chatbot questions) uses it when a key exists; detect mode uses the rule planner unless `PLANNER_MODE=llm`; any LLM failure falls back to the rule planner and a templated answer. The LLM gets the pipeline's numbers and flags as text, never a photo | Detect mode stays deterministic and free per photo; no photo (and so no person) ever leaves AWS for an LLM |
| Weather off in the Lambda (`SENTINEL_WEATHER=off`); the surge rule still raises `notify` / review | No outbound dependency per photo; FlyBot has its own weather service for the chatbot |

## Detector

| Decision | Why |
|---|---|
| **YOLO26n**, end-to-end head (`[1, 300, 6]`, no NMS), on the OpenCV 5 DNN new engine; YOLOv7-tiny kept as the baseline and the AMB82 edge model (`DETECTOR=yolo26|yolov7`) | Test mAP@50 0.953 vs 0.958 (within noise), mAP@50-95 0.700 vs 0.67, same counts on the 24 sample photos, DNN 1.4x faster on CPU, no NMS code; OpenCV 5 matches ONNX Runtime detection for detection (`models/MODEL_CARD.md`) |
| Both YOLO26 heads are decoded (end-to-end and one-to-many with NMS in Python) | If an OpenCV build lacks an op of the end-to-end graph, the fix is a different export, not new code |
| **Class-agnostic NMS on both YOLO26 heads, then fruit-fly box rules** (score >= 0.35, side <= 0.12 and >= 0.004 of the photo, 0.25-3x the photo's median box, aspect <= 4; `DETECTOR_*` variables, `DETECTOR_BOX_RULES=off`). Not done: suppressing boxes that stay in place across photos | The end-to-end head still left duplicate boxes; the owner saw the trap's lens and a lizard counted as flies. Test F1 0.8788 -> 0.9006, the 24 sample photos 15 -> 0 false flies (`models/MODEL_CARD.md`, `eval/results/yolo26_box_rules.json`). Dead flies stay in place in a lure trap, so a persistence rule would remove real catches |
| **Tiled detection by trap kind** (`DETECTOR_TILES` = `off` / `on` / `sticky` / `auto`, default `off`; `sticky` = 2x2 windows with 12 % overlap on sticky-trap photos, boxes cut by an inner window edge dropped, class-agnostic NMS and the box rules in full-frame pixels). The default stays `off`: turning it on changes the counts of EZVIZ users with sticky traps, so it is the owner's deploy setting (`DETECTOR_TILES` in deploy.env -> `DetectorTiles`). A median-box-size trigger (`auto`) was tried and hardly ever fires | YOLO26n letterboxed whole-frame to 640 misses flies under ~20 px at its input. On the synthetic sticky card of the ESP32 trap (detector step, 339 clean photos) `sticky` takes recall 0.04 -> 0.81, precision 0.67 -> 0.86, MAE 43.2 -> 5.1 flies; through the whole handler (demo-30d, 129 clean sticky photos) recall 0.07 -> 0.82, MAE 36.7 -> 5.0, lure counts unchanged. Lure photos are not tiled (`on` would trade lure precision 0.98 -> 0.90 for recall 0.87 -> 0.93). Cost: 4 forwards instead of 1 per sticky photo, `detect()` p50 128 -> 510 ms on the laptop CPU, paid twice when prevPhoto is sent; not measured on the Lambda. `auto` tiled 9 of 339 sticky photos at 24 px because the whole-frame pass finds only the largest flies (`eval/results/synth_tiles.json`, eval/SYNTHETIC_RESULTS.md) |
| The weights are baked into the Lambda image; the public model bucket (`models/yolo26/`, sha256 checked) is the fallback fetched at cold start | The function works offline from S3 and stays reproducible from public files |
| After the contest the commercial build moves to RF-DETR (Apache-2.0) with weights trained on private data in a private bucket | The public entry stays open and reproducible; production data and weights stay private |

## Infrastructure

| Decision | Why |
|---|---|
| **One command, one settings file**: `deploy.env` + `./deploy.sh` (preflight, discover, models, secrets, stack, flybot, image, lambda, bootstrap, health, smoke, coldstart, summary), idempotent, with `--dry-run`, `--only`, `--show-ip`, `--rollback` | One file to fill once; everything the AWS CLI can look up or create (IoT endpoint, AMI, public IP, confirmed alarm topic, quotas, secrets, model upload, builds) is done by the script |
| **FlyBot runs as a prebuilt release**: built on the deploying computer (`npm ci`, `npm run build`), a tarball with its sha256 in a private artifacts bucket, a pointer `flybot/current.json` the server follows; the server runs `npm ci --omit=dev` and `node server/dist/app.js` under systemd, switches releases atomically and keeps the previous one (`--rollback`). Replaced: Docker Compose with the image built on the server from a git clone | The server needs no GitHub access (no deploy key or token on it), no Docker and no build RAM: a t4g.micro (1 GB) is enough, about 7.7 USD/month less. A release changes no CloudFormation property, so it never restarts the instance |
| **FlyBot releases are GitHub pre-releases** of agrhub/flybot-aws (`flybot-<commit>`, named "FlyBot <commit> (deploy build)", notes with branch, commit, build date and sha256), uploaded by deploy.sh with a fine-grained token that never leaves the deploying computer; the server downloads the asset anonymously and checks the sha256 from the S3 pointer. The artifacts bucket stays as the fallback (`FLYBOT_RELEASE_STORE=s3`, or no token). `--prune-releases` keeps the newest 5 | Releases are visible and downloadable without AWS credentials; pre-releases with a "deploy build" name are not mistaken for product releases; the pointer stays in S3 so a release never changes the stack |
| **Clean, small release**: the tarball takes the client files from `client/dist` (FlyBot's copy step leaves older hashed bundles in `server/dist`, 54 MB) and leaves the six home-page and manual videos (188 MB) out; they are published once to the artifacts bucket, synced to the server and served by Caddy before the request reaches FlyBot (`FLYBOT_MEDIA=bundled` keeps them inside). 222 MB -> 16.5 MB | No change to FlyBot; a release download and install take seconds; the videos are transferred only when they change |
| **The host logic is a published script**, not the user-data: the EC2 user-data only writes the stack's values to `/etc/flybot/stack.env` and runs `s3://<artifacts>/host/bootstrap.sh` (`infra/host/bootstrap.sh`), which deploy.sh publishes and re-runs through SSM | A UserData change stops and starts the instance; after this one-time switch, host changes never do |
| **Payments** settings and keys (PayOS, Stripe) live in the app secret like the other FlyBot keys, and follow deploy.env exactly (emptying a key removes it); `PAYMENTS_ENABLED=true` is refused with `APP_MODE=b2b`; the summary prints the two webhook URLs | Switching payments on or off is a secret change and a FlyBot restart, never a stack change; no key on the server's disk |
| **The Lambda image is built by CodeBuild** (ARM small, from a zip of the build context in the artifacts bucket), tagged with a hash of its inputs and built only when that tag is not in ECR. Replaced: a build on the server through SSM | No Docker on the laptop or the server; re-running the deploy costs nothing when the code did not change |
| Host software from upstream with checks: Node 22 from nodejs.org (SHASUMS256), Caddy from its GitHub release (sha512), MongoDB 7 from repo.mongodb.org (signed packages) | Current versions on Amazon Linux 2023 arm64 without containers; each download is verified |
| **MongoDB**: on the server by default (WiredTiger cache 0.25 GB, data on the EBS volume), or an external database through `MONGO_URI` (a secret) | Zero setup for a demo; production can use a managed database. A shared database also receives FlyBot's start-up migrations, which the settings file says |
| **Photo storage**: a stack bucket by default; an existing AWS bucket by name (the roles get access, the bucket is never created, changed or deleted by the stack); or S3-compatible storage (`S3_ENDPOINT`), where FlyBot gives the Lambda presigned URLs and evidence goes to a small stack bucket | The variables are FlyBot's own (`S3_BUCKET_NAME`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`); no FlyBot change was needed |
| Secrets (`flybot-<stage>-app`, `-gcp`, `-anthropic`) are owned by the script, not the stack: merged from `deploy.env` (non-empty values win; keys added in the console are kept; `MONGO_URI` and the storage keys follow `deploy.env` exactly), JWT and VAPID generated once, written only when the content changed | CloudFormation would regenerate or ignore them; the script compares without printing values, and destroy can keep them |
| FlyBot's environment file on the server (`/etc/flybot/env`, mode 600) holds names, ARNs and switches written by the user-data; secrets are read from Secrets Manager at start-up with the instance role | Nothing to copy by hand to the server and no secret on its disk (the Google key for the chatbot is the one file, mode 600, because its client needs a file) |
| The AMI is pinned by the stack after the first deploy; the photo bucket is retained on stack deletion and reused | A newer AMI or a recreated stack would otherwise replace the instance (and a local MongoDB) or lose the photos |
| The IoT endpoint and the AMI are looked up with the CLI and passed as parameters | The public SSM AMI alias is not readable in this account, and the IoT data endpoint is an account fact CloudFormation cannot resolve |
| DNS stays at the registrar: the record is printed as soon as the Elastic IP exists; the health step looks once (1.1.1.1 and 8.8.8.8 over HTTPS) and never waits | agrhub.com is not in Route 53; Caddy obtains the certificate by itself once the name resolves |
| Alarms: Lambda errors (>= 3 in 5 min), Lambda p90 > 30 s, EC2 status check, to a topic with an already confirmed email when one exists | No second confirmation click for the same address |
| Remote commands through SSM Run Command; port 22 only from `OWNER_CIDR`; IMDSv2 required | No SSH key to manage |

## Cameras and live view

| Decision | Why |
|---|---|
| IoT: thing type `camos-camera`, one device policy `camos-camera-<stage>` with per-thing wildcards (`camos/${iot:Connection.Thing.ThingName}/*`, the thing's shadow topics); Connect only when the certificate is attached to the thing named like the client id | Each certificate can act only as its own thing; IoT Core caps a policy at 2,048 characters, so one wildcard per topic tree |
| Zero-touch self-registration (`docs/CONTRACTS.md` 2a): FlyBot signs the camera's CSR (`CreateCertificateFromCsr`, no IAM resource scoping), creates the thing and its KVS channel; the instance role's thing actions are limited to `thing/*` + `thingtype/camos-camera`, certificate and policy actions to `cert/*` + `policy/camos-camera-<stage>`, KVS to `channel/cam-*/*` | FlyBot is the only party that talks to AWS IoT for public cameras; no secret is compiled into the public firmware |
| Device messages reach FlyBot through its MQTT-over-WebSocket subscriber (SigV4); IoT HTTPS rules to FlyBot only when `DEVICE_EVENTS_URL` is set | One path to operate; the rules are the documented fallback and need a one-time destination confirmation |
| KVS live view: a role `flybot-kvs-viewer-<stage>` (viewer actions on `channel/cam-*/*`) that only the instance role may assume; FlyBot narrows each 15-minute session to one channel | The browser never holds the server's credentials; the blast radius is one channel for 15 minutes |

## Repository

| Decision | Why |
|---|---|
| Licensing: this repository (vision Lambda, agent, infrastructure, benchmark, evaluation), the FlyBot app (`flybot/`, AGPL-3.0-only after 1.5.0) and the ESP32-S3 firmware are AGPL-3.0. All three repositories are public. The AMB82 firmware, production datasets and production weights are not published | One copyleft license across the parts that run as a network service. Tests, the sample replay and the local Lambda never need the FlyBot submodule, so the entry is reproducible without it |
